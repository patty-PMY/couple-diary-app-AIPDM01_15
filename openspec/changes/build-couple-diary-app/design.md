# Design

## Context

目前專案只有產品需求文件，沒有應用程式程式碼、既定平台或後端。目標是同時支援 iOS 與 Android，且帳號、配對與共享內容必須可靠地同步並限制在配對雙方之間。產品行為見 `proposal.md` 與 `specs/`。

## Goals / Non-Goals

**Goals:**
- 以一套程式碼建置 iOS 與 Android MVP。
- 提供帳號、雙人配對及共享資料的持久化服務。
- 在後端執行配對範圍授權與輸入驗證。
- 支援重要日期倒數及使用者可選的提醒。

**Non-Goals:**
- 本變更不包含公開社群、照片上傳、聊天、付費訂閱或完整商業分析平台。
- 不承諾離線編輯後自動合併衝突或即時推播同步。
- 不在本階段定案正式營運的資料保存年限與法務文件內容。

## Decisions

### 1. 使用 Expo React Native 與 TypeScript

採用 Expo React Native 建置 iOS／Android 共用用戶端，功能模組以配對、行程、重要日期及日記分開。這符合跨平台需求，也適合目前沒有既有程式碼的專案。替代方案是 Flutter；兩者皆可跨平台，但此方案選擇 TypeScript 生態以便共用型別及 API 契約。若實作團隊已有 Flutter 經驗，應在開工前重新確認此決策。

### 2. 使用 Supabase Auth、PostgreSQL 與 Row Level Security

以 Supabase 提供帳號驗證和 PostgreSQL 資料庫。共享資料表包含 `couple_id`，透過資料庫 Row Level Security (RLS) 驗證目前使用者是否為該配對成員；用戶端介面隱藏功能不構成授權。邀請接受流程使用資料庫交易，避免同一使用者同時加入兩組配對。替代方案是 Firebase；選擇關聯式資料庫是因為配對與多類共享資料需要一致的關聯和約束。

### 3. 以配對作為共享資料邊界

資料模型至少包含使用者、配對、單次邀請、行程、重要日期、日記、留言及心情記錄。行程、重要日期與日記資料保存建立者及所屬 `couple_id`；留言與心情資料透過所屬日記或配對關聯授權。邀請使用一次性隨機代碼，接受後失效。未配對使用者只能存取個人帳號與待接受邀請，不得讀取任何配對內容。

### 4. 由伺服器確認共享操作結果

新增日記、留言、行程和重要日期時，由後端驗證登入狀態、配對成員資格及欄位規則後再回報成功。用戶端在收到成功回應前保留輸入內容；錯誤時顯示失敗狀態。MVP 採取重新整理或重新進入頁面載入最新共享資料，不要求即時同步。

### 5. 使用本機排程提醒，保持提醒可選

每位使用者可自行開啟重要日期提醒。用戶端取得配對的重要日期後，依使用者裝置時區排程本機通知；使用者拒絕通知權限時，倒數仍可正常使用。日期型紀念日以當地日曆日期保存，具體時間型行程保存時間及時區資訊，避免跨時區顯示偏差。

### 6. 將字數及空白驗證集中定義

日記與留言的字數上限及非空白規則必須在用戶端與後端一致驗證；後端是最終依據。字元長度以 Unicode code point 計算，與 PostgreSQL `char_length` 一致，並在介面顯示剩餘字數。日記及留言不會因每日未輸入而阻擋使用者使用其他功能。

## Risks / Trade-offs

- [託管服務可用性、費用及資料所在地受 Supabase 方案影響] → 開發前確認服務區域、預算與備份方式，並避免把服務金鑰放入行動用戶端。
- [RLS 設定錯誤可能洩漏伴侶私密資料] → 對每個共享資料表設定預設拒絕政策，並在實作階段驗證跨配對讀取及寫入均遭拒。
- [本機提醒依賴裝置權限與排程狀態] → 權限被拒時仍保留倒數功能；提醒不可作為唯一的日期呈現方式。
- [行動網路中斷可能造成操作失敗] → 明確顯示載入、成功與失敗狀態，失敗時保留輸入，不宣稱離線操作成功。
- [跨平台通知和日期顯示行為可能不同] → 在 iOS 與 Android 分別驗證時區、夏令時間與權限流程。

## Migration Plan

目前沒有既有應用程式或資料可遷移。先建立開發與測試環境及資料表，再部署後端授權政策，之後發布行動用戶端測試版本。若要回退，停止用戶端發佈並停用新版本存取；刪除或重建資料庫前須先確認是否有測試資料需要保留。

## Open Questions

- 正式環境的 Supabase 專案、資料區域、備份與營運負責人須在部署前指定。
- 本變更只規劃受邀情侶參與的 MVP 測試；若要公開上架，需另行確認正式隱私權政策、資料保存及帳號刪除流程。
