# 重要日期與個人提醒

## 功能

- 配對雙方可新增、查看、編輯及確認刪除重要日期，保留原建立者及所屬配對。
- 日期以 `YYYY-MM-DD` 儲存，倒數依裝置的日曆日期計算，不以固定 24 小時相減，避免夏令時間偏差。
- 每年重複以原始月日計算下次發生日；延續原有日期計算方式，2 月 29 日在非閏年順延至 3 月 1 日，介面會說明此規則。
- 每位使用者可各自開啟、停用提醒，或設定提前 0 至 30 天，提醒時間為登記時區的上午 9 點。編輯共享日期不會改變任何人的提醒偏好。
- 拒絕通知權限時仍可關閉提醒並儲存日期、查看倒數。已啟用但系統權限被撤回時，介面提示至系統設定開啟權限。
- 本機預覽會保存日期及提醒偏好，並清楚標示不會實際發送通知。

## 通知同步與年度派送

單次日期依下一個尚未過期的提醒時間排入本機通知，已過期不補發。每年日期由 Supabase 定時工作逐年計算，不需要重新開啟 App 補排。推播與本機通知都只顯示「你有重要日期提醒，開啟 Our Days 查看」，詳細名稱與日期留在 App。

每次啟動、回到前景、重新整理或異動時同步單次通知與年度推播裝置時區。年度推播沿用最後登記的時區；App 關閉期間改變所在地不會自動更新伺服器時區。首次年度推播註冊前須明確開啟並閱讀資料使用說明；既有本機提醒偏好不會自動視為推播同意。

本機通知使用帳號及日期識別碼去重；年度派送使用提醒、裝置及發生日期的唯一工作鍵與 lease。修改日期或提醒會取消未送出的舊工作；停用或刪除日期會連帶移除派送工作。年度推播在後端讀取最新狀態，單次本機通知則於各裝置下次同步時取消。推播供應商已接受的通知無法撤回；供應商接受後、結果回寫前故障，重試仍有重複投遞可能。

登入狀態切換時取消舊帳號本機通知，登出前移除伺服器上的此裝置登記並清除本機排程。暫時無法取得日期資料時保留同帳號本機通知。排程或裝置註冊失敗時顯示提示，可重新整理重試，不把日期儲存成功誤報為日期失敗。

## 資料庫更新

依序套用既有遷移後，新增套用 `20261111030000_anniversary_management.sql` 及 `20261111040000_annual_push_reminders.sql`。

遷移允許伴侶更新共享日期，並禁止改寫建立者、配對、ID 及建立時間；拒絕空白名稱及無限日期。`create_anniversary` RPC 以呼叫者權限在同一交易建立日期與首次個人提醒，受 RLS 保護，只開放 authenticated 角色執行。個人提醒仍以 `user_id = auth.uid()` 限制存取。

本次未套用至託管 Supabase；已在隔離 PostgreSQL 驗證。

## 驗證

- 型別檢查與 lint 通過。
- `expo export --platform ios` 及 `expo export --platform android` 通過，產生兩平台 Hermes 程式包；此項不代表已完成實機通知驗收。
- 6 個單元測試套件、35 項測試通過，包含倒數、裝置註冊同意、token 註冊、登出移除與本機排程，另在 `America/New_York` 時區驗證夏令時間交界。
- 隔離 PostgreSQL 共 12 項檢查通過，涵蓋重要日期 CRUD、個人提醒隔離，以及同一裝置未重新註冊下連續多年派送、跨年、閏年、夏令時間、去重、lease 逾時、取消及服務 RPC 授權。
- `node --test dispatcher-check.mjs` 的 6 項模擬 HTTP 測試通過，驗證通用文案不含日期名稱或日期、Supabase 服務金鑰不送給 Expo、端點授權、傳輸重試、取消工作及無效 token／receipt 處理。不實際發送推播。
- 通知 API 測試涵蓋重複同步去重、編輯後重新排程、停用與刪除取消、權限被拒、排程失敗後重試、切換帳號、同步途中登出，以及資料載入失敗時保留同帳號通知。

## 實機驗收待辦

原生通知 API 使用 mock；尚未在 iOS／Android 裝置觀察實際投遞。依任務 5.3，使用開發用戶端驗證權限、前景／背景投遞、時區切換、修改日期、停用、刪除及兩台裝置各自設定提醒。APNs／FCM、網路及系統省電狀態會影響投遞。

## 年度推播部署

1. 在 Expo 專案設定 iOS APNs 與 Android FCM 憑證，將專案 UUID 填入 App 的 `EXPO_PUBLIC_EAS_PROJECT_ID`，建立開發用戶端。
2. 在測試用 Supabase 套用上述資料庫遷移，部署 `supabase/functions/dispatch-annual-reminders`。`supabase/config.toml` 停用平台 JWT 檢查，程式會強制驗證專用的 `REMINDER_DISPATCH_SECRET`。
3. 在 Edge Function Secrets 設定至少 32 字元隨機派送密鑰；Supabase 提供的服務金鑰僅在此後端使用。若 Expo 啟用額外推播安全設定，另外設定 `EXPO_ACCESS_TOKEN`，該 token 僅送往 Expo。
4. 啟用 Supabase 的 pg_cron、pg_net、Vault，在 Vault 登記 `annual_reminder_url` 與相同的 `annual_reminder_secret`，再執行 `supabase/deploy/annual-reminders-cron.sql`，每分鐘派送一次。不要把真實密鑰寫入 Git。
5. 使用測試裝置明確開啟年度提醒，查核 Cron、派送工作、Expo ticket 與 receipt；ticket 表示服務收件，不等同於手機已顯示。留意重試耗盡、receipt 失敗及定時工作未執行。

本次只完成程式、腳本與離線驗證，未部署定時工作或實際發送推播。年度提醒在上述部署與裝置登記完成後才會運作。

Expo SDK 58 通知 API 依據：[官方版本文件](https://docs.expo.dev/versions/v58.0.0/sdk/notifications/)。
