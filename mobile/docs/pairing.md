# 伴侶邀請與配對狀態

請依檔名順序套用 `supabase/migrations` 的三份 migration。新增的 `20261111010000_pairing_lifecycle.sql` 提供配對狀態 RPC、等待邀請時的共享資料限制，以及資料庫層的兩人成員上限。勿將本機驗證用的 bootstrap 套用到託管 Supabase。

## 使用流程

1. 兩位使用者各自完成註冊及登入。
2. 一人建立邀請碼並分享，另一人在配對頁貼上完整的 48 字元代碼並接受邀請。
3. 建立者在等待畫面每 10 秒更新狀態，也可手動重新整理。第二人加入後，雙方都會顯示配對成功並可進入共享空間。
4. 邀請有效期為 48 小時、限使用一次。遺失邀請碼、重新開啟畫面或邀請過期時，建立者可產生新碼，先前未接受的碼會失效。伺服器只保存邀請碼雜湊，明碼僅在目前畫面顯示。
5. 已建立邀請或完成配對的使用者無法加入另一組；兩位使用者中只需一人建立邀請。

## 狀態與帳號

- 未配對：沒有成員紀錄，可建立或接受邀請。
- 等待伴侶：只有建立者一名成員，無法讀寫共享資料。
- 已配對：恰有兩名成員，可依既有 RLS 存取共享內容。
- 載入或錯誤：共享頁面不開放，提供重新整理與登出。

應用程式回到前景時會重新讀取配對狀態。登出以本裝置為範圍，成功後清除記憶體中的共享資料與配對狀態；失敗時會顯示錯誤。登入帳號改變時立即清除舊資料，較早發出的資料請求不得覆寫新帳號狀態。預覽資料仍僅存於本機並與真實配對分開。

## 驗證

在 `mobile` 執行 `npm.cmd test -- --watch=false`、`npm.cmd run typecheck` 及 `npm.cmd run lint`。在 `mobile/supabase/validation` 執行 `npm.cmd run verify`。

資料庫驗證使用隔離的 PostgreSQL 與 Supabase Auth 契約模擬，涵蓋邀請格式、失效與過期、已使用代碼、重複配對、兩人成員上限、未登入 RPC 拒絕，以及兩種同時接受邀請的競爭條件。六張共享表另驗證等待邀請、其他配對與未配對帳號的存取限制。RLS 對無權限的讀取及更新／刪除會回傳零筆，新增則回報權限錯誤。

這些檢查不包含託管 Supabase Auth HTTP 服務或 iOS／Android 實機操作。部署新 migration 後，仍需以兩個測試帳號在裝置上走完邀請、分享、接受、重新登入及登出流程。
